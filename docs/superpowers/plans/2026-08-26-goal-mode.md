## 1. How the reference implementations actually do it

### 1.1 OpenAI Codex (rust-v0.128.0+, PRs #18073–#18077)

Five stacked PRs. The load-bearing insight is in PR #18073's own words:

> "Goal mode needs durable thread-level state before clients or model tools can safely build on it."

- **State layer first**: a `thread_goals` table keyed by thread, with status
  (`active / paused / budget_limited / complete`), objective text, and usage
  accounting (time + tokens charged against the goal). Updates carry a
  `goal_id` so a stale write can never overwrite a replacement goal
  (optimistic concurrency).
- **App-server APIs**: create / replace / update / delete / account-usage.
  The TUI's `/goal <objective>` goes through this API — it is *not* sent to
  the model as a prompt.
- **Model tools**: the model gets goal tools on turns where a live goal
  exists; it reports progress/completion through them rather than through prose.
- **Runtime continuation**: when a turn ends while the goal is still active,
  the runtime admits the next turn itself. This is what makes a goal a loop
  instead of a sticky note.
- **TUI** (#18077): `/goal` renders a summary (active/paused/budget-limited/
  complete); `/goal <objective>` create-or-replace **with a confirmation menu**
  when a goal already exists; `/goal clear|pause|resume`; footer/statusline
  indicator with elapsed time + token budget; end-of-turn desktop
  notifications are **suppressed while a goal is active** (the run isn't done
  just because one turn ended); goal updates/clears from external clients keep
  the TUI in sync via notifications.

Community framing calls the resulting loop "Ralph": plan → act → test → review → iterate until stop condition, user pause, or budget exhaustion.

### 1.2 DeepSeek Harness family (dsh standard mode ships "plan and goal state"; Orca's `docs/goal-mode.md` is the most complete public spec)

Orca (dsh-derived) documents the full machine. What matters for us:

- **One GoalActor owns the state machine**; SQLite is authoritative; every
  transition commits once per *outer* turn (one outer turn = one admitted
  provider/tool loop; inner tool calls never advance counters).
- **Persist-before-cancel ordering**: an active `/goal pause` writes
  `Paused(user)` *before* cancelling the generation, so a user stop can never
  be rewritten as an infrastructure failure.
- **Rich pause taxonomy**: `paused(user | no_progress | infrastructure |
  recovery | waiting_for_workflow)`, `blocked`, `budget_limited`,
  `complete`. Crash with a turn in flight → next owner marks
  `Paused(recovery)` and does NOT call the provider; resume starts a fresh run.
- **Continuation admission gate** — continue only when ALL of: goal active, no
  cancellation pending, **no user steer input queued**, no approval/permission
  pending, not in plan mode, budget remains. Every admit/reject emits a reason-coded event.
- **No-progress stall guard**: 3 consecutive outer turns repeating the same
  model-fixable gap (or 8 consecutive budget-stop turns) → auto-pause as
  stalled. Side-effecting tool calls or structured-plan changes count as
  substantive progress and reset the streak; prose and read-only exploration do not.
- **Typed internal context**: the goal lives as a replaceable-by-id internal
  fragment rendered as a synthetic system message — **never appended to user
  messages or tool results**, preserving prompt-cache prefix stability for the
  real transcript. Inactive goal ⇒ fragment removed.
- **Continuation envelope**: each continued turn receives objective,
  continuation trigger, previous end reason, budget snapshot, open-gap
  fingerprint, task-plan snapshot, bounded previous-assistant checkpoint, plus
  an explicit instruction to verify current state and resume rather than restart.
- **Terminal intents from the model**: `get_goal / create_goal / update_goal`
  tools; `update_goal` returns a typed ack (`DeferredToTurnEnd`,
  `AlreadyPending`, `Rejected`, `BlockedAgainstInactive`). Completion requires
  evidence; `blocked` must classify the blocker
  (`user_decision | missing_authority | external_state |
  environment_contradiction | unverifiable_requirement`). Orca verifies
  terminal claims with a separate verifier call; that is their v2 weight.

### 1.3 T3 Code (pingdotgg/t3code)

T3 Code is a control surface over provider CLIs — it has no native goal
feature of its own (nothing in `docs/user/`); a "goal" there would be Codex's
feature proxied through the provider adapter. Its transferable lessons are
architectural conventions Atlas already follows, restated here because they
bind this feature:

- Commands → persisted events → projected read model; the UI projects, it
  never reconstructs a second state machine.
- "Reverse states": if you add a way in (set/pause), add the way out
  (resume/clear). One-way doors are bugs.
- Entry points: a behavior reachable from the composer should also be visible
  in the transcript/status surfaces; fixing one surface is not fixing the feature.

### 1.4 Synthesis — what Atlas copies, adapts, defers

| Mechanism | Source | Atlas decision |
|---|---|---|
| Durable per-thread goal row w/ revision guard | Codex #18073 | Copy. New `conversation_goals` table, `revision` column for stale-update protection |
| `/goal` talks to state API, not the model | Codex | Copy exactly |
| Runtime continuation after settle | Codex + Orca | Copy, hooked into ChatEngine settle path |
| Admission gate (steer/approval/plan/budget) | Orca | Copy, minus workflow/plan-mode clauses Atlas lacks |
| Persist-before-cancel on pause | Orca | Copy — order is DB write then abort |
| Stall guard (no side-effecting tool call N turns) | Orca | Copy, simplified (v1: 5 turns) |
| Typed internal-context fragment, replaced by id | Orca | Adapted: system-reminder block injected per turn while goal active; removed when inactive |
| Continuation envelope message | Orca | Copy — synthetic steer text for continued turns |
| Model terminal-intent tool w/ typed acks | Orca/Codex | Copy shape (`update_goal`), defer separate verifier LLM call |
| Evidence-gated completion | Orca | v1: require ≥1 evidence item + ≥1 side-effecting tool call this goal; full verifier deferred |
| Token budget + time budget | Codex | Field reserved in schema; v1 enforces **turn cap** only (default 25) |
| Footer indicator, notification suppression, replace confirmation | Codex TUI | Copy all three |

## 2. Atlas design

One goal per conversation. Owned by a new main-process `GoalRuntime` (pure
state transitions + admission decision), persisted in SQLite, projected to the
renderer over IPC events. The renderer never mutates goal state directly — it
asks.

### 2.1 Data model

New table (schema.ts migration, FK cascade on conversations):

```sql
CREATE TABLE IF NOT EXISTS conversation_goals (
  id TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  objective TEXT NOT NULL,                -- user text, ≤4000 chars
  status TEXT NOT NULL DEFAULT 'active',  -- active|paused_user|paused_stalled|
                                          -- paused_recovery|complete|blocked|cleared
  blocker_kind TEXT,                      -- for blocked: user_decision|missing_authority|
                                          -- external_state|environment_contradiction|unverifiable_requirement
  blocker_note TEXT,
  revision INTEGER NOT NULL DEFAULT 1,    -- stale-update guard (Codex goal_id analog)
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  turn_count INTEGER NOT NULL DEFAULT 0,
  turn_cap INTEGER NOT NULL DEFAULT 25,
  tokens_in INTEGER NOT NULL DEFAULT 0,   -- accounted from 'meta' stream events (observability v1)
  tokens_out INTEGER NOT NULL DEFAULT 0,
  last_progress_turn INTEGER              -- turn index of last substantive-progress signal
);
CREATE UNIQUE INDEX idx_conversation_goals_active
ON conversation_goals (conversation_id) WHERE status NOT IN ('cleared');
```

Partial unique index enforces one live goal per conversation. `cleared` rows
are history (audit trail like Orca's transition journal, kept cheap).

New repo `conversationGoalsRepo`: `getActive(conversationId)`,
`create(objective)`, `replace(objective)` (bumps revision, archives old row),
`transition(goalId, fromStatus, toStatus, patch)` (guarded UPDATE … WHERE
revision/status — returns false on stale), `accountUsage(goalId, tokens)`,
`recordProgressTurn`.

### 2.2 Main-process GoalRuntime (`src/main/ai/goal/GoalRuntime.ts`)

Pure-ish module holding no Electron types; ChatEngine wires it in. API:

```ts
create(convId, objective): GoalSummary          // replaces existing (archive+new)
pause(convId): GoalSummary                      // persist BEFORE caller aborts generation
resume(convId): GoalSummary                     // paused_* → active (+admission re-check)
clear(convId): GoalSummary|null
getActive(convId): GoalSummary|null
// ChatEngine callbacks:
onTurnSettled(convId, info: {turnIndex, aborted, failed, hadSideEffectingToolCall}): void
onTurnUsage(convId, tokens:{in:number,out:number}): void
```

**Admission gate** (runs in `onTurnSettled`, mirrors Orca):

Continue ⇔ goal.status === 'active'
  && !aborted && !failed                       // failed → paused_infrastructure is v2; v1: just don't continue
  && no queued followups for conv              // ChatEngine knows its queue
  && no approvals pending for conv             // approvalController
  && workspaceMode !== 'plan'-equivalent       // n/a yet; clause reserved
  && turn_count < turn_cap

On continue: `turn_count += 1`, stall check
(`turn_count - last_progress_turn >= 5` → `paused_stalled`, emit rejected event),
else enqueue continuation turn (below) and emit `goal.continuation.admitted`.
Every reject emits `goal.continuation.rejected {reason}` into activities.

**Stall progress definition**: `hadSideEffectingToolCall` — bash (non read-only
heuristic already used elsewhere is fine to approximate: any bash/edit/write/git-write
tool terminal) or `update_plan` call during the turn. Prose never resets the streak.

**Terminal intents**: the model claims completion via the `update_goal` tool
(§2.4). GoalRuntime records the intent; transition to `complete`/`blocked`
commits at turn settle (deferred-to-turn-end semantics, matching Orca without
their verifier): if evidence non-empty AND the goal has ≥1 recorded progress
turn → accept; malformed args → recoverable tool error (`Rejected` ack);
claim against non-active goal → `BlockedAgainstInactive`. `blocked` requires
a valid `blocker_kind`.

### 2.3 Prompt injection + continuation envelope

While a goal is active, ChatSessionRuntime appends ONE system-side block after
canonical instructions (same slot family as `JOB_TOOL_SYSTEM_PROMPT`,
ChatSessionRuntime.ts:1131 pattern — conditional, so inactive goals change nothing):

```
GOAL_SYSTEM_PROMPT prefix (prefix-stable):
"A persistent goal is active for this conversation..."
Then the typed envelope (changes per turn — acceptable cache cost, matches Orca):
objective, status, turn x/of cap, continuation trigger (user-set | auto-continue),
previous end reason, open-stall note if streak > 0, and:
"Verify current state before continuing. Do not restart exploration you have
already done. Report progress or completion with update_goal; completion
requires concrete evidence (commands run, files changed)."
```

Never appended to user messages or tool results (Orca rule).

**Continuation turns** reuse the existing followup machinery
(ChatEngine.followupQueue): on admission, ChatEngine enqueues a synthetic
request whose text is the fixed steer line:

`<system-reminder>Goal continuation (auto): continue working toward the active goal. Re-verify current state first.</system-reminder>`

This inherits queueing, status events, checkpoint capture, and dispatch
ordering for free — no second scheduler. Origin tagged `'goal'` so
`sendMessage` telemetry can exclude it.

### 2.4 Model tool: `update_goal` (`src/main/ai/tools/goalTools.ts`)

Registered only when `workspace.goalRuntime && goal active` (same gate shape
as jobTools/terminalTools — withheld means uncallable). Not approval-gated;
not side-effecting (it requests a state change, the runtime decides).

```ts
update_goal({
  status: z.enum(['complete','blocked']),
  reason: z.string().min(1).max(500),
  evidence: z.array(z.object({ kind: z.enum(['test','build','file_change','manual_check']),
                              summary: z.string().max(300),
                              target: z.string().max(300).optional() })).min(1),
  blocker_kind: z.enum([...]).optional(),   // required when blocked
})
→ ack: 'DeferredToTurnEnd' | 'Rejected: <why>' | 'AlreadyPending' | 'BlockedAgainstInactive'
```

`get_goal` omitted in v1 — the system-prompt envelope already carries the
state every turn (one less tool; Orca advertises get_goal because their
envelope is thinner).

### 2.5 IPC + preload + contracts

Channels (shared/ipc.ts): `goalsSet`, `goalsPause`, `goalsResume`,
`goalsClear`, `goalsGet`, push channel `goalsEvent`.

Contracts: `ConversationGoalSummary {id, objective, status, blockerKind?,
blockerNote?, revision, createdAt, updatedAt, turnCount, turnCap, tokensIn,
tokensOut}`; request payloads `{conversationId, objective?}`. Push payload
`{type:'updated'|'transitioned'|'continuation_admitted'|'continuation_rejected',
conversationId, goal}` — renderer store subscribes once, filters per pane
(same shape as jobsEvent handling).

Preload namespace `atlasChat.goals.{set,pause,resume,clear,get,onGoal}`.

Pause ordering enforced in IPC handler: `repo.transition(paused_user)` THEN
`chat.abort(currentRequestId)` — persist-before-cancel (Orca).

### 2.6 Renderer

- **Store**: `goalByConversation: Record<string, ConversationGoalSummary>`;
  bootstrap fetch for selected conversation lazily (getPage-style, only when
  dock visible or slash used); subscription updates map.
- **GoalDock component** (`components/goal/GoalDock.tsx`) rendered inside the
  composer dock stack directly above QueueDock (both are "work still owed"
  strips — same visual grammar, border-t hairline):
  - one row, truncated objective (title attr for full), status chip
    (active=accent dot pulse-once, paused=muted, complete/blocked=terminal tone),
    `turn 7/25`, buttons: Pause⇄Resume, Edit (inline textarea swap, Enter saves
    via goalsSet → confirm-free since edit keeps same goal id), Clear (confirm
    dialog — reverse-state rule: clear is destructive history-wise).
  - hidden entirely when no active/recent goal (QueueDock precedent).
- **Slash command**: extend `slashCommands.ts` — new
  `parseSlashCommandWithArgs(draft)` returning `{name, args}`; standalone
  parser delegates to it. Composer submit path: `/goal` bare → dock focus/summary
  toast; `/goal <text…>` → goalsSet (rest of line verbatim, trimmed, ≤4000);
  `/goal pause|resume|clear|edit <text?>` variants; replacement-with-existing
  shows ConfirmDialog (Codex menu analog). Autocomplete description:
  "Set a persistent objective the agent keeps working toward across turns".
- **Transcript visibility**: goal lifecycle writes `conversation_activities`
  rows (`goal.created`, `goal.paused`, `goal.resumed`, `goal.completed`,
  `goal.blocked`, `goal.continuation.admitted|rejected`) via the existing
  activity recorder — audit trail without new UI; activity blocks render them
  like followup events do.
- **Notification suppression**: while `status==='active'`, suppress the
  end-of-turn attention bump for background windows (C2 attention projection
  gains a goal-aware precedence note; needs-input/failed still surface).

### 2.7 Fork/delete interactions

- Fork: goals are NOT copied (fork copies work product; a goal is intent for
  *this* thread). Side chats likewise. Documented in conversationFork header table.
- Delete: CASCADE removes goal rows with the conversation.
- App crash mid-turn: on boot reconcile — active goal whose conversation has
  no running turn stays active (it simply continues on next admission tick);
  no special recovery state in v1 (Atlas has no multi-process contention; single window owner).

## 3. Explicit non-goals (v1)

- Separate verifier LLM call for terminal claims (Orca's verification step) —
  evidence-shape checks only; revisit after real usage.
- Token/time budgets enforced as hard stops (columns + accounting ship; enforcement = turn_cap only).
- Parallel goals per conversation, cross-conversation goals, goal templates.
- Cloud-sandbox turns participating in goal accounting.

## 5. Risks / open questions

- **Runaway loops** are THE failure mode of this feature class. Mitigations
  shipped: hard turn cap, stall guard, admission gate, every continuation
  event logged, Pause one click away, notifications suppressed but Activity
  bell still lists the running conversation (C2 unchanged).
- **Cache invalidation**: envelope changes per continued turn → system-prompt
  prefix breaks each continuation. Bounded (~1 break per turn, only in goal
  mode). If it hurts, move envelope below history as trailing system-reminder
  user-message like job notices (mechanism exists) — decide by measurement.
- **Approval interplay**: approvals pause continuation naturally (gate), but a
  long-pending approval leaves goal 'active' + idle forever; add v1.1: auto
  `paused_user` when an approval ages past N minutes? Open question for review.
- **Multi-window**: two windows same conversation — goal state is main-process
  owned; both projectors receive pushes. No lease needed (single process).
