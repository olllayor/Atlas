Atlas vs T3 Code — Performance Architecture Review

Sources: /Users/ollayor/Code/Projects/Atlas @ bdf4db1 (dev) and pingdotgg/t3code @ HEAD, shallow-cloned for analysis. All file paths and numbers below were read from the actual source trees on 1 Sep 2026. Atlas renderer: 395 files, ~103k LOC of TS/TSX. t3code: pnpm monorepo (apps/desktop, apps/web, apps/server, apps/mobile + packages/contracts, packages/client-runtime, effect-acp, effect-codex-app-server, native/).

1. Verdict first

Atlas is not "unoptimized". It already ships four techniques that are the same ideas t3code uses: a 33ms stream coalescer in the main process, a virtualized transcript with a self-calibrating height estimator, a paged conversation cache with eviction, and a lazy-loaded markdown pipeline.

The "heavy" feeling comes from five specific, fixable gaps:

  • A single eager 5.0 MB main bundle — everything (Settings, Plugins, Sites, xterm, visual gallery, XAI landing page) is parsed and executed on every launch.
  • App.tsx subscribes to ~40 store fields at once, so every stream token re-renders the entire app tree (Sidebar included) because nothing below it is memoized.
  • Transcript rows are not memoized — only the inner MessageResponse is, so per-token work scales with the visible window, not with the one row that changed.
  • Streaming state lives in the global store instead of being scoped to the one conversation/row that is live.
  • Heavy work (diff render, markdown for long threads) stays on the renderer main thread, where t3code uses a web-worker pool and process isolation.

t3code's deeper advantage is cultural, not structural: they measure budgets ("first paint on the heaviest threads stays ~100K gzipped"), they bound worst cases, and they audit regressions (their AGENTS.md literally lists "too much data over websockets, CSS animations causing GPU spikes, lists being hard to render" as standing audit targets).

3. What T3 Code actually does (evidence)

3.1 Per-thread atoms with idle-TTL eviction

Thread state is not React state. Each thread gets its own atom from an Atom.family, backed by a SubscriptionRef, and unmounted threads release memory after a 5-minute idle TTL — back-navigation stays instant, but memory is bounded to recently-used threads.

// packages/client-runtime/src/state/threads.ts:703-719
const family = Atom.family((key: string) => {
  return runtime.atom(threadStateChanges(environmentId, threadId), {
    initialValue: EMPTY_ENVIRONMENT_THREAD_STATE,
  }).pipe(
    Atom.setIdleTTL(THREAD_STATE_IDLE_TTL_MS),
// threadRetention.ts: THREAD_STATE_IDLE_TTL_MS = 5 * 60_000

Why it matters for Atlas: a token arriving in conversation A currently re-renders conversation B's shared parent components, because both read one global store. Scoped atoms/selectors make that cross-talk structurally impossible.

3.2 Measured pagination budgets

// threads.ts:43-50
export const INITIAL_THREAD_USER_TURN_LIMIT = 10;    // first paint
export const OLDER_THREAD_PAGE_USER_TURN_LIMIT = 20; // per "load older"
// "Sized so first paint on the heaviest observed threads stays
//  around 100K gzipped while median threads load fully."

They picked user turns as the unit because subagent fan-out turns ride along, and the number came from measurement, not taste.

3.3 Snapshot over HTTP, deltas over WebSocket, cursor resume

Multi-KB snapshots travel over compressible HTTP with a hard 6s timeout (so a slow endpoint can't block the cheaper socket fallback); deltas resume via afterSequence, so a warm cache never re-downloads a thread body.

3.4 Pure reducers with an "unchanged" terminal state

// threadReducer.ts:44-60
export type ThreadDetailReducerResult =
  | { readonly kind: "updated"; readonly thread: OrchestrationThread }
  | { readonly kind: "deleted" }
  | { readonly kind: "unchanged" };

The server broadcasts every event to every subscriber; unchanged makes cross-thread event storms free — SubscriptionRef only notifies on real change. Atlas's reducers already return null in this case (streamEventReducers.ts:373-375) — same idea, worth keeping.

3.5 Heavy work off the renderer main thread

  • Diff parsing: dedicated web-worker pool — apps/web/src/components/DiffWorkerPoolProvider.tsx:62.
  • Terminal VT parsing: native/WASM (native/libghostty-vt), not JS.
  • Host telemetry: Rust child process (native/resource-monitor).
  • Preview tabs: separate webContents with their own preloads and caches — a heavy preview can never jank the chat UI.

3.6 Lazy everything at the panel level

// apps/web/src/components/ChatView.tsx:505-509
const PreviewPanel = lazy(() => import(...));
const DiffPanel = lazy(() => import("./DiffPanel"));
const FilePreviewPanel = lazy(() => import("./files/FilePreviewPanel"));

Desktop preloads are separate tiny cjs artifacts with explicit alwaysBundle allow-lists; web dev can run Vite's bundled-dev mode so remote browsers don't pay a round trip per import level.

3.7 Performance as a written, audited invariant

AGENTS.md:15-18: "We regularly audit for performance regressions, often caused by sending too much data over websockets, css animations causing gpu spikes, lists being hard to render, and more." The machinery is consistently bounded: ring buffers with byte budgets, LRU caches, debounced write-behind persistence, latest-wins command lanes, idle TTLs. They bound worst cases, not just averages.

4. What Atlas already does right (keep these)

  • Stream coalescer in main — ChatEngine.ts:105 (STREAM_BATCH_INTERVAL_MS = 33, i.e. one IPC flush per frame) with a pure, unit-tested merge contract (streamBuffer.ts). This is exactly t3code's "don't flood the socket" discipline.
  • Virtualized transcript with adaptive height calibration — ChatWindow.tsx:1148-1197: estimates are continuously corrected against real measurements with a decaying accumulator, so the scrollbar stays honest on long threads.
  • Paged + evicting conversation cache — conversationCache.ts: 100-message pages, compact on deactivate, evict beyond 3 inactive conversations, cursor-based "load older".
  • Lazy markdown module — lib/messageRendering.ts + LazyMessageResponseContent; shiki grammars and mermaid/cytoscape are already separate chunks in out/renderer/assets/.
  • Null-returning pure reducers — unchanged events cost zero state writes.
  • xterm WebGL renderer for the terminal — the right call.

5. Recommendations, prioritized

P0Break the per-token re-render of the whole app

App.tsx:342 subscribes via one useShallow selector with ~40 fields (settings, models, conversations, …), and ChatWindow receives detail as a prop. Every stream token replaces conversationDetails[id], so the entire App subtree — Sidebar, workbench, dock — reconciles per token. Neither Sidebar nor MessageRow is memoized.

  • Wrap MessageRow in React.memo (props are message + stable callbacks — cheap change, big effect).
  • Split the App-level selector: view-routing fields stay in App; conversation-detail fields move to a hook used only by ChatWindow.
  • Longer term (t3code-style): move the streaming draft into its own store slice subscribed only by the streaming row, so a token can't touch conversationDetails at all.

P0Split the 5 MB eager bundle

out/renderer/assets/index-*.js is 5,068 KB executed on every launch (assets dir totals 21 MB, but mermaid 2.6 MB / shiki grammars / cytoscape are already lazy chunks — the monolith is the problem). Candidates that are visibly not on the critical path:

// Route/panel-level lazy boundaries (same as t3code ChatView):
const SettingsWorkspace = lazy(() => import('./SettingsWorkspace'));    // 2019 lines
const PluginsWorkspace  = lazy(() => import('./plugins/PluginsWorkspace'));
const SitesWorkspace    = lazy(() => import('./sites/SitesWorkspace'));
const XAILandingPage    = lazy(() => import('./XAILandingPage'));
const TerminalDock      = lazy(() => import('./workbench/TerminalDock')); // xterm
const VisualGallery     = lazy(() => import('./ai-elements/visual-gallery'));
// + manualChunks in electron.vite.config.ts renderer.rollupOptions:
//   vendor-react, vendor-ai (ai + @ai-sdk/*), vendor-xterm, vendor-motion

P1Move diff rendering off the main thread

t3code parses diffs in a worker pool (DiffWorkerPoolProvider.tsx). Atlas's DiffBlock.tsx and the changed-files pipeline run on the main thread — noticeable when an agent turn touches many files. A single pool of 2–4 workers with a request queue is a contained change.

P1Adopt measured budgets

t3code's pagination constants cite a measured payload budget. Atlas has the knobs (DEFAULT_CONVERSATION_PAGE_SIZE, INACTIVE_CONVERSATION_CACHE_LIMIT) but no documented measurement. Add one script that opens the heaviest real conversation, records first-paint ms and JS heap, and pins those numbers in a comment next to the constants. Regressions then get caught in review, not by feel.

P2Bounded animations and rAF loops

t3code explicitly audits CSS animations for GPU spikes; Atlas has hand-rolled rAF loops (status-dot.tsx's own comment says it once animated a transform per frame) plus Rive WebGL canvases. Ensure every Rive instance is paused when off-screen and every infinite CSS animation is gated behind prefers-reduced-motion and visibility.

P2Persistence write-behind

If any high-frequency renderer state (composer drafts, transcript UI) is persisted synchronously, debounce it into a write-behind queue like t3code does; drafts are the usual offender.

P3Process isolation for artifacts/previews

t3code runs previews in separate webContents. Atlas's HTML artifact sandbox should get the same treatment when it grows: a hostile generated page must never be able to jank the transcript.

P3Tooling upgrades

Atlas is already on TypeScript 7. Swapping tsc --noEmit in CI for native (tsgo-style) checking and adopting oxlint are dev-velocity wins, mirroring t3code's vite-plus/tsgo/oxlint choice.

6. Summary of my thoughts

Atlas's problems are concentrated and fixable; t3code's edge is that performance is a tested invariant there, not a vibe. In priority order the wins are:

  1. Memoize MessageRow + split App's giant selector — hours of work, removes the per-token whole-app render (the single biggest "heavy" feeling).
  2. Lazy-load the settings/plugins/sites/terminal/landing surfaces + vendor chunks — removes ~2–3 MB of parse/exec per launch.
  3. Scope streaming state so tokens can't touch shared store slices.
  4. Worker-pool the diff pipeline.
  5. Then adopt t3code's culture: measure budgets, write them next to the constants, audit regressions.

Atlas's coalescer, virtualizer, and paged cache are genuinely at t3code's level. The gap is bundle discipline, subscription granularity, and main-thread isolation. Close those three and the app will feel dramatically lighter without an architecture rewrite.

One correction. Its claim that "T3 put shiki inside a Web Worker (worker-CIcqvLjo.js is a shiki build)" does not hold up in source: chat-markdown highlighting in t3code runs in-thread via use(getSyntaxHighlighterPromise(language)) with preferredHighlighter: "shiki-js" (apps/web/src/components/ChatMarkdown.tsx:969, lib/syntaxHighlighting.ts:10), guarded by an LRU cache of highlighted HTML. The worker chunk they saw in the minified bundle is the diff worker (DiffWorkerPoolProvider.tsx). The recommendation itself (get tokenizing off the UI thread) is still sound — t3code just does it with caching + the diff worker, not a shiki worker.

Minor framing quibble: "bundle size is not the difference" is directionally right for the streaming feel (t3code's entry is comparably large), but ~5 MB of parse/eval still costs real cold-start time on weaker machines — which its own item 5 (entry down a third) acknowledges. Both halves are worth doing; they are not in conflict.
