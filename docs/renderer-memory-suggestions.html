Process
Reaped live

Kill orphaned OpenCode servers on startup

Our process check verified the audit report: PID 74684 is currently running on this machine with PPID 1: 

ollayor 74684     1  0 Thu05PM ??  22:43.08  /Users/ollayor/…/bin/opencode2 serve --register

The mechanism is in src/main/ai/providers/opencode/OpenCodeRuntime.ts:282: 

const child = this.childFactory(command, args, {
  stdio: ['ignore', 'pipe', 'pipe'],
  detached: process.platform !== 'win32',
  windowsHide: true,
});

Setting detached: true creates a new process group so Atlas can signal the entire group on clean shutdown. However, when Electron restarts during electron-vite dev or crashes, the parent death reparents the detached process directly to launchd (PID 1). The process never receives SIGTERM or SIGHUP.

Proposed fix

  • Add startup orphan reaping. In OpenCodeController.ts during boot, execute a quick check using pgrep or process table inspection for any command containing opencode serve or opencode2 serve whose parent PID is 1. Send SIGTERM, wait 500ms, escalate to SIGKILL if still responsive.
  • Record active PIDs in a session lockfile. Write the child PID to app.getPath('userData')/opencode.pid on spawn, and delete it on clean shutdown. On launch, check that PID before spawning a new instance and ensure previous sessions do not accumulate.
  • Bind lifecycle via stdin pipe. Instead of stdio: ['ignore', ...], pass a pipe for stdin. If Atlas dies unexpectedly, the pipe closes on the OS side, signaling EOF to the child.
File panel
Root cause 1

Virtualize the file viewer and cap tokenization

src/renderer/components/workbench/FileViewerPanel.tsx accepts files up to the 2 MB limit defined in WorkspaceIndex.ts:39 (FILE_BYTE_CAP = 2 * 1024 * 1024) and passes the whole text to CodeBlock.tsx.

Inside CodeBlock.tsx:231-244, renderHighlightedCode iterates over every token of every line: 

{line.map((token, tokenIndex) => (
  <span key={`token-${lineIndex}-${tokenIndex}`} style={tokenStyle(token, variant)}>
    {token.content}
  </span>
))}

For a 1,000-line file, this produces 9,452 <span> elements, 9,452 CSSStyleDeclaration instances, and 24,199 React FiberNodes. For a 20,000-line file, it will produce over 200,000 DOM nodes, instantly triggering a 100 MB+ heap spike that ratchets macOS physical footprint upward permanently.

Proposed fix

  • Virtualize file lines using TanStack Virtual. Atlas already lists @tanstack/react-virtual: ^3.13.12 in package.json. Virtualizing the line list in FileViewerPanel keeps the rendered DOM count under 60 rows at all times, whether the file has 100 lines or 50,000 lines.
  • Enforce a syntax highlighting ceiling. For files larger than 1,200 lines or 60 KB, fall back to plain text or highlight only the visible scroll slice. A plain text block in renderPlainCode uses one span per line with zero inner token spans and zero inline style objects.
  • Eliminate per-token style object allocations. tokenStyle() computes a new JavaScript style object for each token during render. Using CSS custom properties or pre-rendered HTML strings injected via dangerouslySetInnerHTML into the line container removes thousands of transient object allocations per frame.
Terminal
Root cause 2

Limit scrollback buffer and throttle high-frequency IPC

The terminal panel in src/renderer/components/workbench/TerminalPanel.tsx:293 hardcodes scrollback: 10_000. On this branch, users can open multiple split panes per terminal tab and multiple terminal surfaces across conversations.

When a command emits megabytes of output, two things happen:

  1. In src/main/terminal/PtyService.ts:154, pty.onData immediately fires IPC events to the renderer for every 4 KB to 64 KB chunk without buffering. Under heavy output, thousands of discrete string transfers flood Electron IPC, triggering constant GC cycles in both main and renderer processes.
  2. In TerminalPanel.tsx:361, terminal.write(event.data) parses escape codes and expands xterm's circular buffer up to 10,000 lines. Even after the command finishes or the user clears the screen, the dirtied pages remain compressed in macOS memory and accounted in phys_footprint.

Proposed fix

  • Reduce default scrollback to 2,500 lines. 10,000 lines is excessive for auxiliary split panes. Reducing to 2,500 lines cuts peak memory retention per pane by 75% without compromising standard developer terminal history.
  • Batch terminal chunks in PtyService. During rapid output bursts, aggregate data over an 8ms window before calling this.emit(). Batching lowers IPC serialization overhead by an order of magnitude and prevents V8 heap thrashing.
  • Purge buffer on tab dispose. When closing a terminal tab, call terminal.reset() before terminal.dispose() to release circular line buffers immediately rather than leaving references to decay.
Transcript
Root cause 3

Stop eager line splitting during streaming

The audit recorded a development instance climbing from 3.18 GB to 7.37 GB over 40 minutes while streaming eight concurrent conversations, including one turn with 274,774 characters of input.

Investigating src/shared/toolCellGrammar.ts:411-421 reveals the cause: 

const allLines = splitLines(text);
const { lines, omitted } = truncateHeadTail(allLines);
return {
  type: 'text',
  lines,
  allLines,
  head: omitted > 0 ? TOOL_OUTPUT_MAX_LINES : lines.length,
  tail: omitted > 0 ? TOOL_OUTPUT_MAX_LINES : 0,
  omitted,
  empty: false,
};

Every single tool call executes splitLines(text) immediately and stores allLines in memory, even when the cell starts collapsed.

Worse: during tool execution, as text streams in chunk by chunk, buildToolCells(parts) runs on every flush in ChatWindow.tsx:965, ToolCell.tsx:131, and WorkbenchPanel.tsx:424. A 200 KB output streaming over 50 deltas re-splits the entire growing text 50 times, generating tens of thousands of discarded string fragments.

When expanded or in RawToolCell, TerminalBlock.tsx:228 feeds all lines into AnsiLines, running regex parseAnsiLine over thousands of rows and creating tens of thousands of DOM elements.

Proposed fix

  • Lazy line slicing. Extract the first 5 lines (head) and last 5 lines (tail) using indexOf('\n') and lastIndexOf('\n') scans without materializing the full allLines array when collapsed.
  • Throttle grammar execution during streaming. Do not re-parse multi-kilobyte tool outputs on every incoming token. Throttle grammar recomputation to 100ms intervals while a tool is actively running.
  • Cap rendered lines in expanded terminal blocks. In TerminalBlock.tsx, render at most 200 lines into the DOM, with a button to "Copy full output" or open in the FileViewer surface.

Metric

Anchor automated tests to phys_footprint

The existing Playwright memory scripts in scripts/perf/ (memProbe.mjs, procSampler.mjs, sampleLoop.mjs) already record phys_footprint alongside RSS and JS heap metrics.

Standard performance monitors that only check process.memoryUsage().heapUsed or resident set (RSS) miss the macOS compressor ratchet completely. To prevent regressions:

  • Add a footprint budget test to CI. Run node scripts/perf/memProbe.mjs --scenario fileChurn as an automated benchmark. Assert that cycling 10 file opens leaves renderer footprint below 200 MB.
  • Add pre-commit check for untracked imports. Run git status --porcelain or a clean clone verification in GitHub Actions so untracked file regressions are caught before PRs land.
